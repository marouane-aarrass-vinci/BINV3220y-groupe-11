Parcours d’affichage des offres

Gesta est une application web en npm workspaces : le frontend React/TypeScript (Vite) consomme une API Express/TypeScript, qui lit SQLite avec better-sqlite3. La route des offres illustre les échanges entre ces couches.

Du composant React à la base, puis retour à l’écran

1. Route et page

frontend/src/App.tsx rend OffersPage sur /offres si le profil peut consulter les offres. La page appelle useOffers et affiche chargement, erreur, état vide ou tableau.
→

2. Hook et service HTTP

frontend/src/hooks/useOffers.ts déclenche le chargement, gère l’annulation et les erreurs 401. frontend/src/services/offers.service.ts envoie GET /api/offers avec le jeton brut dans Authorization, puis valide le JSON avec isOfferList.
→

3. Proxy et route protégée

En développement, Vite transmet /api/offers au backend en retirant /api. backend/src/app.ts installe l’authentification et branche le contrôleur backend/src/controllers/offers.controller.ts. La permission canListOffers refuse les profils sans accès.
→

4. Règles métier

backend/src/services/offers.service.ts choisit les offres visibles : toutes pour l’administrateur, publiées pour l’étudiant, déposées par le contact déposant. Le contrôleur convertit ensuite les offres en DTO de réponse.
→

5. SQL et données

backend/src/repositories/offers.repository.ts exécute une requête SQL qui joint les offres aux entreprises, années académiques et périodes, applique le filtre d’accès et trie les résultats. Le schéma correspondant est défini dans backend/src/db/migrations/001_initial.sql.
→

6. Conversion et affichage

backend/src/mappers/offer.mapper.ts transforme les lignes SQL en objets métier puis en DTO. Le frontend valide le DTO, le hook le fournit à OffersPage, puis frontend/src/components/OfferTable.tsx affiche titre, entreprise, année, période et statut.

Fichiers à examiner pour ajouter un filtre par période

  • frontend/src/pages/OffersPage.tsx : état/sélection du filtre et transmission de la période choisie.
  • frontend/src/hooks/useOffers.ts : intégrer la période aux paramètres de chargement ou filtrer localement, selon le comportement voulu.
  • frontend/src/services/offers.service.ts : sérialiser une période dans la query string si le filtrage est effectué par l’API.
  • backend/src/controllers/offers.controller.ts : lire et valider le paramètre de requête avant l’appel au service.
  • backend/src/services/offers.service.ts : combiner le filtre de période avec les règles de visibilité existantes.
  • backend/src/repositories/offers.repository.ts : ajouter le critère SQL correspondant à periods.code.
  • backend/tests/offers.test.ts et frontend/tests/OffersPage.test.tsx : couvrir validation, filtrage et interface.
  • backend/API.md : documenter le paramètre et son comportement.

La période existe déjà dans la table periods, elle est liée à l’offre par period_id et la réponse inclut déjà period. Un filtre n’exige donc a priori pas de migration SQL ; le choix entre filtrage côté client et filtrage côté serveur reste à définir selon le comportement souhaité.

Commandes du projet

À exécuter depuis la racine :

  • npm ci puis npm run setup : installer et initialiser.
  • npm run dev : lancer API et interface.
  • npm run db:init / npm run db:reset : initialiser ou recréer la base.
  • npm run lint : lint ; npm run typecheck : vérifier TypeScript.
  • npm test : lancer les tests Vitest.
  • npm run build : compiler backend et frontend.
  • npm run check : lint, typecheck, tests et build.

Pour un test ciblé, par exemple : npm run test -w backend -- tests/offers.test.ts ou npm run test -w frontend -- tests/OffersPage.test.tsx.
